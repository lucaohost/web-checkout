# Idempotency keys on state-changing kiosk requests

The kiosk's network can drop a response after the server has already acted: the stock is reserved, or the card is charged, and the kiosk never hears about it. Every request that changes state therefore carries a key generated by the kiosk. Resending the request with the same key returns the original result instead of acting twice. The kiosk never chooses the id of any record; it only signals "this is a repeat". Server ids and the Order Code are generated by the server.

## Which requests carry a key

- `POST /checkouts` and `POST /checkouts/:id/payment` require an `Idempotency-Key` header holding a UUID v4. A missing or malformed key is rejected with `400`.
- `GET` requests are safe by nature. `DELETE /checkouts/:id` is idempotent by nature: deleting an already released Checkout returns its final state.

## How the kiosk uses keys

- **One key per Customer intent.** The confirm key is minted for the Cart as it stands, and the pay key when the Customer taps "Pay".
- **Repeats reuse the key.** Resending after a timeout, a dropped connection or an app recovery sends the same key with the same body. If every retry of a confirmation loses its response, the next tap of "Confirm order" on an unchanged Cart is that resend.
- **A new intent gets a new key.** Editing the Cart, confirming again after a `409` (adjusted prices or quantities) and "Try another card" are new intents. Changing the Cart after a confirmation whose response was lost is also a new intent: the kiosk first replays the old key, cancels that Checkout when it is still active, and only then confirms the new Cart. Otherwise the abandoned reservation holds Stock until it expires, and the new body with the old key is a `422`.
- Keys live in memory next to the Cart; the idle reset discards them.

## How the server handles a key

Keys are stored in Postgres ([ADR-0004](./0004-postgres-database.md)) with a unique constraint, together with the kiosk id, the route, a SHA-256 fingerprint of the body, a state (`in_progress` or `completed`), the stored response (status and body) and timestamps.

1. **First request.** The server inserts the key as `in_progress` before doing any work. When two copies arrive at once, the unique constraint lets exactly one of them proceed.
2. **Definitive outcome.** Once the request ends with a definitive outcome (`2xx`, the `402` for a declined or failed payment, or the `409` for checkout conflicts), the response is stored and the key becomes `completed`. Requests rejected by validation (`400`) never record their key.
3. **Same key, same route and fingerprint, `completed`.** The server replays the stored response with the header `Idempotent-Replayed: true`.
4. **Same key, still `in_progress`.** The server answers `409 request_in_progress`, and the kiosk retries after a short backoff. An `in_progress` key older than 30 s, well past the 7 s worst case of a payment, is treated as abandoned by a crashed process, and the next request takes it over.
5. **Same key, different route or fingerprint.** The server answers `422 idempotency_key_reused`. This is always a client bug.
6. **Unexpected error (`5xx`).** The key is deleted and nothing is stored, so a resend runs the request again. This is safe because each side effect underneath is itself idempotent: the Stock Reservation belongs to its Checkout ([ADR-0010](./0010-stock-reservation.md)), and every charge carries its own provider key (below).

Keys expire after 24 hours and are purged by the API's periodic sweep.

## Keys towards the payment provider

The kiosk's key is never forwarded to the payment provider. Each Payment Attempt gets its own provider key, `{checkoutId}:{attemptNumber}`:

- The automatic retry after a Payment Failure reuses the attempt's key, so the provider charges at most once per attempt.
- "Try another card" starts a new attempt, so the attempt number and the key change.
- Status queries (`GET /payments/:key`) and Refunds of an attempt address it by the same key ([ADR-0006](./0006-payment-mock-separate-service.md)).

## Considered options

- **Order id generated by the kiosk.** Rejected. The client would choose the identity of a record, and the Order does not exist until payment is approved or the Customer chooses Pay at Pickup.
- **A token issued by the server before submitting.** Rejected. It adds a round trip whose response can be lost in exactly the same way.
- **Only disabling the button after the first tap.** Rejected as the only defense. It stops double taps but not a lost response followed by a resend. The kiosk does disable the button, as a first layer.
- **Keys kept in API memory or in Redis.** Rejected. Postgres is already there, its unique constraint arbitrates races, and keys survive a restart.

## Consequences

- Each state-changing request costs one extra insert and one update.
- A replayed response describes the moment of the first request. To learn the current state of a Checkout, the kiosk calls `GET /checkouts/:id`.
