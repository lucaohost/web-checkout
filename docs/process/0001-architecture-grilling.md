# 0001: Architecture grilling session

**Date:** 18 October 2026, before any code was written.
**Inputs:** the assignment brief (PDF) and a first draw.io diagram: a flat list of requirements, plus boxes for the tablet, `checkout-api`, a cache, a database and a payment provider.
**Tooling:** Cursor agent driven by the [`grill-with-docs`](../../.cursor/skills/grill-with-docs/SKILL.md) skill, which combines [`grilling`](../../.cursor/skills/grilling/SKILL.md), relentless questioning over a decision tree, with [`domain-modeling`](../../.cursor/skills/domain-modeling/SKILL.md), which keeps the glossary and ADRs current as decisions land.

## How it ran

The agent read the brief and the diagram and built the whole decision tree. It then asked every question at once, each with a recommended answer, so a "yes" accepted the recommendation. Answers that opened new decisions produced a further round. The session took three rounds: 50 questions, then 16, then 8. Documentation was written after each round, only for the decisions already settled.

## Problems found in the first draft

- Retrying the payment without an idempotency key turns a timeout that actually succeeded into a double charge.
- "Validate stock before saving the order" races when two kiosks compete for the last unit.
- Unattended-kiosk risks were missing: the next Customer seeing the previous Cart, double taps, a network drop mid-payment.
- The diagram showed no frontend process, no separate payment mock, no observability, no flow and no states.
- Both existing ADRs were numbered `0001`, and the backend ADR justified Node with "many simultaneous connections" and "multiple teams", premises a snack-bar kiosk does not have.

## Where the human overrode or reshaped the agent's recommendation

These are the decisions that changed the design the most:

| Topic | Agent recommended | Decided | Effect |
| --- | --- | --- | --- |
| When an Order exists | Create it before paying, with payment statuses | Only after a card approval, or a Pay at Pickup choice | Introduced the **Checkout** and the **Stock Reservation** ([ADR-0010](../adr/0010-stock-reservation.md)) |
| Prices | Server recalculates silently | Server recalculates and tells the Customer about any change | Price conflicts in the same `409` as stock conflicts |
| Payment methods | Simulated card terminal only | Also cash, as **Pay at Pickup**, the fallback after any failed card attempt | [ADR-0012](../adr/0012-card-payment-retry-unknown-refund.md) |
| Forcing errors in the demo | Hidden panel behind five taps on the logo | Cut; headers set by a browser extension | [ADR-0006](../adr/0006-payment-mock-separate-service.md) |
| Menu cache expiry | 5 s | Challenged: at snack-bar traffic a 5 s cache would almost never hit. Became 5 min, Menu only, Stock never cached | [ADR-0011](../adr/0011-menu-cache-in-memory.md) |
| Stock conflicts | Reject the whole Checkout | Remove or reduce only what is short, keep the rest, and require explicit confirmation | [ADR-0010](../adr/0010-stock-reservation.md) |
| Repeated requests | Order id generated by the kiosk | Questioned why; became an `Idempotency-Key` header, with server-generated ids | [ADR-0009](../adr/0009-idempotency-keys.md) |
| Order statuses | Only Paid and Payment Pending | Also Picked Up and Cancelled | Staff endpoints and a staff key ([ADR-0013](../adr/0013-order-lifecycle-staff-endpoints.md), [ADR-0008](../adr/0008-kiosk-security-baseline.md)) |
| Unknown payment outcome | Flag the Order and leave reconciliation for later | Also send a Refund to the provider | Background Refunds with retries and an alert |
| Receipt | No printing | Simulated printing | Receipt step in the flow |
| Cancelling returns Stock | Accepted | Accepted, with the waste caveat documented | [ADR-0013](../adr/0013-order-lifecycle-staff-endpoints.md) |
